# Mentor Teaching Guide

Resources for teaching robotics programming to students of all experience levels.

## Teaching Philosophy

### Core Principles

**1. Start Simple, Build Gradually**
- Begin with concrete examples
- Add complexity gradually
- Check understanding before moving on
- Celebrate small wins

**2. Multiple Learning Styles**
- **Visual**: Diagrams, flowcharts, demos
- **Auditory**: Explanations, discussions
- **Kinesthetic**: Hands-on coding, simulation
- **Reading**: Documentation, examples

**3. Make It Relevant**
- Connect to real robot applications
- Show how concepts solve problems
- Use competition scenarios
- Demonstrate practical value

**4. Encourage Questions**
- Create safe environment for asking
- No "stupid" questions
- Learn from misunderstandings
- Ask "What do you think?" often

## Quick Lesson Planning

### 45-Minute Lesson Template

**Objective**: Students will understand and use [concept]

#### Opening (5 minutes)
- **Hook**: Show robot doing something cool
- **Question**: "How does the robot know...?"
- **Preview**: What we'll learn today

#### Direct Instruction (10 minutes)
- **Explain concept**: Simple language + analogy
- **Show example**: Live coding demo
- **Explain code**: Line by line walkthrough

#### Guided Practice (15 minutes)
- **Code together**: Everyone writes same code
- **Test frequently**: Run and see results
- **Debug together**: Fix errors as class

#### Independent Practice (15 minutes)
- **Similar task**: Small variation of example
- **Work in pairs**: Students help each other

#### Closing (5 minutes)
- **Recap**: What we learned
- **Demonstrate**: Show working examples

## Teaching Activities

### Activity 1: Concept Relay (15 minutes)

**Purpose**: Collaborative learning through code completion

**How it works**:
1. Divide into teams of 3-4
2. Each student completes one part of code
3. Pass to next student to add their part
4. Test and debug together

**Debrief questions**:
- "What was hard about your part?"
- "How did you decide what to write?"
- "What would you do differently?"

### Activity 2: Live Debugging (20 minutes)

**Purpose**: Learn debugging by watching expert think aloud

**Process**:
1. Show buggy code
2. Ask: "What do you think is wrong?"
3. Try suggestions (even wrong ones)
4. Explain why each works/doesn't
5. Fix bug together

### Activity 3: Analogies First (10 minutes)

**Purpose**: Build understanding through comparisons

**Process**:
1. Present technical concept briefly
2. Ask students to create analogies
3. Share best analogies
4. Refer back to analogies during lesson

**Example**: PID Controllers
- Thermostat (temperature)
- Cruise control (car speed)
- Following someone (distance)

## Student Assessment

### Quick Understanding Checks

**Thumbs Up/Down/Sideways**:
- "Thumbs up if you understand this"
- "Sideways if you're kind of confused"
- "Down if you're totally lost"

**Pair-Share**:
- Explain concept to your partner
- Partner explains it back
- Both people explain

**One-Minute Paper**:
- Write what you learned today
- Write what's still confusing
- Share with class

### Code Reading Assessment

**Show code and ask**:
- "What does this line do?"
- "Predict the output"
- "How would you fix this?"
- "What's wrong with this?"

### Practical Assessment

**Build working**:
- Subsystem that does X
- Command that accomplishes Y
- Auto routine that achieves Z

**Debug and fix**:
- Broken code (with intentional bugs)
- Performance issues
- Edge cases

## Common Teaching Scenarios

### When Students Are Stuck

**Don't**:
- Give the answer immediately
- Take over the keyboard
- Say "it's easy"
- Move on too quickly

**Do**:
- Ask guiding questions
- Suggest debugging strategies
- Break problem into smaller parts
- Refer to similar examples
- Celebrate persistence

### Questions to Ask

**Understanding**:
- "What do you think this does?"
- "Why did you write it this way?"
- "What would happen if...?"
- "Can you explain this to your partner?"

**Debugging**:
- "What did you expect to happen?"
- "What actually happened?"
- "What's different?"
- "Where should we look first?"

## Building Confidence

### Praise the Right Things

**✅ Do praise**:
- Effort over ability
- Process over results
- Persistence over speed
- Collaboration over individual
- Questions over answers

**❌ Avoid**:
- "That's wrong"
- "You should know this"
- "Why didn't you...?"
- Comparisons to others

### Examples of Good Praise

- "Great question! That shows you're thinking deeply."
- "I like how you kept trying different approaches."
- "You explained that really clearly to your partner."
- "That's a creative solution I hadn't thought of!"

## Common Student Misconceptions

### Programming Misconceptions

**"Computers know what I mean"**
- **Reality**: Computers do exactly what you tell them
- **Fix**: Show code doing exactly what's written
- **Demonstrate**: Run "wrong" code to show it works as written

**"More complex is better"**
- **Reality**: Simple code is better code
- **Fix**: Refactor complex code together
- **Show**: Compare simple vs complex versions

### Robotics Misconceptions

**"Real robot is different from simulation"**
- **Reality**: Simulation is accurate for testing logic
- **Fix**: Test both ways and show results match
- **Explain**: What's different (physics vs real world)

**"Complicated = competitive"**
- **Reality**: Simple, reliable code wins
- **Fix**: Show competition examples
- **Focus**: Reliability and testing

## Quick Reference for Mentors

### First-Time Teaching

**Start with**:
- Topics you know well
- Simple, clear examples
- One concept at a time
- Lots of hands-on practice

**Build confidence**:
- Successful early experiences
- Clear expectations
- Frequent feedback
- Celebrate small wins

### Managing Different Skill Levels

**In same class**:
- Pair different levels together
- Give extension activities to advanced
- Provide extra support to struggling
- Use stations for different topics

**Individual projects**:
- Let advanced students explore
- Give struggling students structured tasks
- Check in frequently with everyone
- Adjust pace as needed

## Assessment Quick Tools

### Exit Ticket Template

```
1. What did you learn today?
2. What's still confusing?
3. What do you want to learn next?
```

### Code Quality Rubric (Quick)

**Excellent (4)**:
- Clear, readable code
- Well-documented
- No bugs

**Good (3)**:
- Mostly readable
- Some documentation
- Minor bugs

**Needs Work (2)**:
- Hard to read
- Little documentation
- Some bugs
