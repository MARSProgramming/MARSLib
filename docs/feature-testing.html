Physics-Backed Testing

Beyond Mocks

Writing tests that simply mock returning values doesn't prove an FRC system works correctly in reality. MARSLib uses JUnit 5 wired directly into our dyn4j physics framework to ensure that tests evaluate real consequences.

How Tests Run

When running ./gradlew test on MARSLib:

  • Realistic Hardware Simulation: E.g. when testing the elevator subsystem to go to a setpoint, our test doesn't mock an encoder. It applies motor voltage to a physics mass on a continuous hinge joint. The test waits for the virtual PID to actually move the virtual mass to the target.
  • Extensive Coverage: We compile close to 90 test cases asserting everything from SOTM polynomial correctness, 250Hz threading integrity, swerve kinematics bounding ranges, to state machine validity.
  • Continuous Integration: All PRs are instantly built and tested on Ubuntu Github Actions runners. Strict linters prevent malformed code from entering master.

Confidence in the Codebase

If our physics tests pass, we know the robot will operate identically on the field. The simulation physics are an exact substitute for real hardware—ensuring a fundamentally sound code repository at all times.
