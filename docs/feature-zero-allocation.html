Zero-Allocation Hot Path

Why Zero-Allocation?

In the high-stakes environment of FIRST Robotics Competition matches, control loop consistency is critical. The RoboRIO's JVM garbage collector (GC) can cause non-deterministic pauses—sometimes lasting upwards of 10-20ms. In a 20ms control loop, a single GC pause can result in skipped loops, jittery odometry, and missed shots.

MARSLib's Approach

MARSLib enforces strict zero-allocation rules on the hot path (the 20ms robot loop and critical subsystems). We achieve this through:

  • Pre-allocated Buffers: Odometry arrays, pose arrays for AdvantageKit, and state containers are instantiated once during robotInit(). We never use new within a periodic function.
  • Static Velocity & Pose Constants: Heavy objects like Transform3d or Rotation2d are cached where possible rather than dynamically generated every tick.
  • Mutating Existing Objects: Instead of creating new arrays to pass data, we mutate pre-defined structured objects inside the hardware IO layers.
  • No Magic Math Boxing: Using primitive double variables everywhere. Avoiding accidental `Double` wrapper boxing that causes hidden garbage collection pressure.

Impact on Performance

By keeping the GC idle during the teleoperated and autonomous routines, MARSLib ensures the robot maneuvers accurately and predictably, even during complex trajectories and rapid swerve module steering.
