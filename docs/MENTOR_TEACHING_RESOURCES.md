# Mentor Teaching Resources

Resources for teaching robotics programming to students of all experience levels.

## Teaching Philosophy

### Core Principles

**1. Start Simple, Build Gradually**
- Begin with concrete examples
- Add complexity gradually
- Check understanding before moving on
- Celebrate small wins

**2. Multiple Learning Styles**
- **Visual**: Diagrams, flowcharts, demos
- **Auditory**: Explanations, discussions
- **Kinesthetic**: Hands-on coding, simulation
- **Reading**: Documentation, examples

**3. Make It Relevant**
- Connect to real robot applications
- Show how concepts solve problems
- Use competition scenarios
- Demonstrate practical value

**4. Encourage Questions**
- Create safe environment for asking
- No "stupid" questions
- Learn from misunderstandings
- Ask "What do you think?" often

## Lesson Plan Templates

### Template 1: Single Concept (45 minutes)

**Objective**: Students will understand and use [concept]

**Materials**: Computers, MARSLib installed, projector

#### Opening (5 minutes)
- **Hook**: Show robot doing something cool
- **Question**: "How does the robot know...?"
- **Preview**: What we'll learn today

#### Direct Instruction (10 minutes)
- **Explain concept**: Simple language + analogy
- **Show example**: Live coding demo
- **Explain code**: Line by line walkthrough
- **Check understanding**: "Does that make sense?"

#### Guided Practice (15 minutes)
- **Together**: Code along with instructor
- **Step by step**: Everyone writes same code
- **Test frequently**: Run and see results
- **Fix errors**: Debug together as class

#### Independent Practice (10 minutes)
- **Similar task**: Small variation of example
- **Work in pairs**: Students help each other
- **Instructor circulates**: Help as needed
- **Early finishers**: Help others or try extension

#### Closing (5 minutes)
- **Recap**: What we learned
- **Demonstrate**: Show working examples
- **Preview**: What's next
- **Questions**: Address confusion

### Template 2: Multi-Day Project (3-5 days)

**Objective**: Students will build [project] using [skills]

#### Day 1: Introduction (45 min)
- Project overview and goals
- Show final example
- Break into components
- Start with component 1

#### Day 2: Development (45 min)
- Review day 1
- Add component 2
- Test integration
- Debug together

#### Day 3: Completion (45 min)
- Add remaining components
- Test full project
- Individual variations
- Share results

#### Day 4-5: Extensions (optional)
- Improve base project
- Add features
- Optimization
- Final showcase

## Teaching Activities

### Activity 1: Concept Relay (15 minutes)

**Purpose**: Collaborative learning through code completion

**Setup**:
- Divide into teams of 3-4
- Each team gets incomplete code
- Each student completes one part

**Process**:
1. Student 1 writes first part (initialization)
2. Pass to Student 2 (adds execute method)
3. Pass to Student 3 (adds isFinished)
4. Student 4 tests and fixes bugs

**Debrief**:
- What was hard?
- What did you learn?
- How would you improve?

### Activity 2: Live Debugging (20 minutes)

**Purpose**: Learn debugging by watching expert think aloud

**Setup**:
- Projector with code
- Known buggy code
- Students suggest fixes

**Process**:
1. Run code, show bug
2. Ask: "What do you think is wrong?"
3. Try suggestions (even wrong ones)
4. Explain why each works/doesn't
5. Fix bug together

**Key**: Make thinking visible - narrate your reasoning

### Activity 3: Analogies First (10 minutes)

**Purpose**: Build understanding through comparisons

**Process**:
1. Present technical concept briefly
2. Ask students to create analogies
3. Share best analogies
4. Refer back to analogies during lesson

**Example**: PID Controllers
- Thermostat (temperature)
- Cruise control (car speed)
- Following someone (distance)

### Activity 4: Code Surgery (15 minutes)

**Purpose**: Learn to read and understand existing code

**Setup**:
- Working code example
- Remove key parts
- Students fill in blanks

**Variations**:
- **Predict output**: What will this do?
- **Find the bug**: Where's the problem?
- **Optimize**: Make this faster/better
- **Explain**: Teach this to a partner

### Activity 5: Robot Tasks (30 minutes)

**Purpose**: Apply learning to realistic scenarios

**Setup**:
- Give specific robot task
- Students design solution
- Implement and test

**Example Tasks**:
- "Drive in a 2m square"
- "Pick up game piece and score"
- "Balance on charging station"
- "Follow line on field"

## Assessment Strategies

### Formative Assessment (Ongoing)

**Exit Tickets** (5 min end of class):
```
1. What did you learn today?
2. What's still confusing?
3. What do you want to learn next?
```

**Quick Checks**:
- "Thumbs up/down/sideways" for understanding
- Pair-share explanations
- One-minute papers
- Concept maps

**Code Reading**:
- "What does this line do?"
- "Predict the output"
- "How would you fix this?"

### Summative Assessment (End of Unit)

**Practical Tasks**:
- Build working subsystem
- Create autonomous routine
- Debug broken code
- Optimize performance

**Questions**:
- Explain concept in plain language
- Teach someone else
- Apply to new situation
- Connect multiple concepts

**Projects**:
- Multi-component systems
- Original contributions
- Documentation
- Teaching materials

## Common Misconceptions

### Programming Misconceptions

**Misconception**: "Computers know what I mean"
**Reality**: Computers do exactly what you tell them

**How to address**:
- Show code doing exactly what's written
- Demonstrate with "wrong" code
- Emphasize precision

**Misconception**: "More complex is better"
**Reality**: Simple code is better code

**How to address**:
- Refactor complex code together
- Show simpler vs complex versions
- Praise elegant solutions

**Misconception**: "If it works, it's done"
**Reality**: Working code can still be improved

**How to address**:
- Code reviews
- Refactoring exercises
- Show maintenance benefits

### Robotics Misconceptions

**Misconception**: "Real robot is different from simulation"
**Reality**: Simulation is accurate for testing logic

**How to address**:
- Test both ways
- Show simulation accuracy
- Explain what's different

**Misconception**: "Complicated = competitive"
**Reality**: Simple, reliable code wins

**How to address**:
- Show competition examples
- Focus on reliability
- Test thoroughly

## Group Work Strategies

### Pair Programming

**Driver** (types):
- Controls keyboard
- Writes code
- Follows navigator's directions

**Navigator** (guides):
- Reviews code
- Catches bugs
- Suggests improvements
- Doesn't touch keyboard

**Switch roles every 10-15 minutes**

### Team Projects

**Roles**:
- **Lead Architect**: Design and structure
- **Implementer**: Write code
- **Tester**: Find bugs and verify
- **Documenter**: Write explanations

**Rotate roles** so everyone practices each skill

## Teaching Tips

### When Students Are Stuck

**Don't**:
- Give the answer immediately
- Take over the keyboard
- Say "it's easy"
- Move on too quickly

**Do**:
- Ask guiding questions
- Suggest debugging strategies
- Break problem into smaller parts
- Refer to similar examples
- Celebrate persistence

### Questions to Ask

**Understanding**:
- "What do you think this does?"
- "Why did you write it this way?"
- "What would happen if...?"
- "Can you explain this to your partner?"

**Debugging**:
- "What did you expect to happen?"
- "What actually happened?"
- "What's different?"
- "Where should we look first?"

### Building Confidence

**Praise**:
- Effort over ability
- Process over results
- Persistence over speed
- Collaboration over individual

**Avoid**:
- "That's wrong"
- "You should know this"
- "Why didn't you...?"
- Comparisons to others

**Instead**:
- "Great question!"
- "Let's figure this out together"
- "What did you try?"
- "What if we tried...?"

## Common Teaching Scenarios

### Scenario 1: Code Won't Compile

**Don't**: Fix it for them
**Do**: 
- Read error message together
- Ask "What does this error mean?"
- Guide to solution
- Celebrate when fixed

### Scenario 2: Student Doesn't Understand

**Don't**: Repeat same explanation
**Do**:
- Try different explanation
- Use analogy
- Draw diagram
- Act it out
- Find different resource

### Scenario 3: Different Skill Levels

**Challenge**: Some get it, some don't
**Solutions**:
- Pair different levels
- Give extension activities
- Use stations
- Flexible grouping
- Peer teaching

### Scenario 4: Short Attention Spans

**Keep engaged**:
- Change activities every 10-15 min
- Mix coding with discussion
- Use real robot examples
- Hands-on activities
- Movement breaks

## Assessment Rubrics

### Code Quality Rubric

**Excellent (4)**:
- Clear, readable code
- Follows conventions
- Well-documented
- Efficient
- No bugs

**Good (3)**:
- Mostly readable
- Some documentation
- Generally efficient
- Minor bugs

**Fair (2)**:
- Hard to read
- Little documentation
- Inefficient
- Some bugs

**Needs Work (1)**:
- Unclear code
- No documentation
- Very inefficient
- Many bugs

### Learning Rubric

**Excellent (4)**:
- Teaches others
- Asks deep questions
- Makes connections
- Applies creatively

**Good (3)**:
- Understands concepts
- Asks questions
- Completes tasks
- Some application

**Fair (2)**:
- Basic understanding
- Few questions
- Struggles with tasks
- Limited application

**Needs Work (1)**:
- Confused by concepts
- No questions
- Can't complete tasks
- No application
